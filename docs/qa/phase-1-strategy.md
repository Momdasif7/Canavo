## Baseline facts used for planning

- **API surface:** 243 route handlers in 20 routers. The largest are inventory (47), delivery (31), tables (23), customers (15), attendance (15) and admin (15). Reports add one dynamic route per report key.
- **Existing automated tests:** 9 Vitest files, about 123 test cases. 28 are in `packages/shared/src/gst.test.ts`; the rest are API unit tests for promotions, inventory, service-context, GSTR-1, crypto, time, IP whitelist and report export. There are no API/HTTP, DB, E2E, load or security suites yet.
- **CI:** `.github/workflows/ci.yml` runs build, unit tests, typecheck and migrate for the root workspaces, plus a mobile typecheck. There's no lint step, no E2E and no scans.
- **Security middleware:** `helmet` is present in `app.ts`. Rate limiting still has to be confirmed (Phase 3/8).

## Decisions and notes

1. **Git:** the project had no repository. I initialised one, committed the existing code as `008952a` on `main`, and created `qa/full-testing`. Nothing is pushed anywhere. `.gitignore` gained QA artefact folders and `apps/mobile/.env`. I checked that no `.env` files were staged.
2. **Test DB:** integration, DB and concurrency tests will use a separate `canavo_test` database, so the demo data you browse stays untouched.
3. **Fixture hotels:** H1 (no GST), H2 (GST registered, all modules) and H3 (composition, multi-outlet) are created by a QA seed in Phase 4/5 work.
4. **Highest-priority risks**, by score: cross-tenant leaks, wrong money/GST, lost or duplicate orders. Then concurrency, missed kitchen tickets, the known tab-split and job double-run gaps, brute force, IST boundaries and performance.
